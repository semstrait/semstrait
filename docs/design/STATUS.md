Changes to §5 (last checkpoint) are mandatory on every spec session. Changes to §§1–4 are only when the underlying state actually changed.

## 7. Lessons learned (append-only)

Short notes on recurring failure modes observed during this exercise. New entries append; existing entries are not edited.

- **L1 (2026-04-17)** — The spec tree must ground every abstraction in current code. Introducing parallel models (e.g. `Binding` where only `ColumnMapping` exists; a unified `data_kinds:` YAML tag where only per-variant plural tags exist; a generic constraint framework with reserved future carriers where only Measure/Metric carry them) is the recurring failure mode. The job is *describe, clean, and name what exists* — not propose alternate abstractions to sugar over existing shapes. Any abstraction that is not in code must be flagged as a proposed extension with explicit justification, not smuggled in as a "natural" generalization.
- **L2 (2026-04-17)** — Prose spelling discipline: YAML-facing noun ≠ internal Rust variant. Conflate them and cross-doc references drift. Maintain both spellings explicitly.
- **L3 (2026-04-17)** — When drafting against a feature-gated crate, distinguish module-level feature flags from crate-level separation. The former is a v1 concern; the latter is a migration-plan concern.
- **L4 (2026-04-17)** — Spec documents hold design definitions, not decision logs. Rationale, "what this doc ratifies / does NOT ratify," divergence analyses, and open-item lists belong in `STATUS.md` or per-doc open-question files, not at the top of the spec itself. Keep the spec body pure: structure, types, grammar, rules, diagnostics.
- **L5 (2026-04-17)** — Generics are a tool, not a goal. A generic umbrella like `BodyType<Public, Nested>` reads worse than two named concrete structs when the two forms differ in field set. Prefer concrete Public / Nested types with per-variant bodies; reach for generics only when two forms share a field set exactly and the common field set outweighs the naming cost.
- **L6 (2026-04-17)** — When a "generic base" contradicts "per-variant rules" (e.g. a single `ComplexDataKind` struct that simultaneously enumerates concrete children AND bans self-nesting per arm), switch to an enum-of-bodies shape. Structural constraints that differ across variants belong on the variant, not on the base; the base should only hold genuinely universal fields.
- **L7 (2026-04-17)** — "Is-a" relationships (e.g. "a `Dataset` is a `DataKind`") belong in the type system, not in prose. Composition (`has-a`) alone cannot express them: a caller cannot write a generic function bounded by "is a data kind" when `DataKind` is a struct. The remedy is a sealed trait hierarchy: a base trait for the universal interface and marker / accessor sub-traits for each classification axis (structural vs behavioral in our case). Marker traits are cheap — their value is the bound itself. Pair the trait hierarchy with view enums so heterogeneous iteration still has an exhaustive `match` against concrete variants; the views implement the common trait subset, letting the same bound work on a single concrete, a `&dyn Trait`, or a `ViewRef<'_>`.
- **L8 (2026-04-17)** — When a shared infrastructure piece (I/O, diagnostics, config) has to live somewhere, the choice between "new sibling crate" and "new module in `core` behind a feature flag" is a real trade-off, not a reflex. A sibling crate *feels* cleaner but adds a workspace edge, a `Cargo.toml`, a CI matrix cell, and forces every downstream to declare a second dependency — with no additional isolation when every crate would end up depending on it anyway. A feature-gated `core` module preserves core's zero-runtime-dep posture *only if* the feature is strictly opt-in (`default-features = false` restores zero deps) AND the module exposes only the transport vocabulary — domain wrappers (`load_model`, `load_manifest`, …) must stay in their owning crates, otherwise you pull every downstream into core's dependency graph. Rule: transport in core (gated, opt-in); domain in owning crate; no wrapper fan-in. When in doubt, re-run the test: "if I set `default-features = false` on every crate in the workspace, does `cargo tree` show zero runtime deps on core's `io` module?" — if no, the placement is wrong.
- **L9 (2026-04-17)** — When the broader ecosystem already ships a battle-tested abstraction for a commodity concern (I/O transport, HTTP, async-runtime glue), the default answer is *thin-wrap*, not *reinvent*. The hand-rolled version always looks simpler on day one — then collects retry policy, multipart uploads, credential chains, proxy config, streaming decoders, and a dozen S3-compatibility bugs over the next two years. Thin-wrapping `object_store` for `core::io` replaced ~300 LOC of glue with trivial delegation and unlocks GCS / Azure / HTTP as ~30-LOC additive MINORs each. Two discipline rules survive the wrap: (1) the ecosystem crate is an *internal* detail — never re-exported except through one documented escape hatch (`S3SourceBuilder::with_object_store_builder`); (2) our trait surface stays small enough that swapping the wrapped crate later is an internal-only change. The litmus test: "could we swap `object_store` for `opendal` without breaking a single downstream crate?" — if yes, the encapsulation is right. Separately: when asking the user "library depth?" questions, show the *concrete* trade-off table (transitive deps, API stability, license, dep cost under `--no-default-features`) rather than abstract pros/cons — it shortens the decision loop dramatically.
- **L10 (2026-04-17)** — Closing a surface end-to-end benefits from a **consolidation doc** separate from the root doc. `32c_entities.md` was added as a sibling to `32_semstrait_model.md` rather than bloating `32` itself; the separation makes the root doc remain navigable (structure-level truths: root YAML shape, DataKind hierarchy, Extras composition, SR-*) and concentrates the entity-level cross-cuts (Relationship grammar, TemporalShape, Dimension / Measure / Metric shape, filter taxonomy, SemanticMapping value shape) where they compose cleanly. The pattern: *root doc for container, sibling doc for contained*. Applying the same split prophylactically will help when Constraints lands (its natural home is a new `32d_constraints.md` referenced from `Measure` / `Metric` definitions in `32c`), and again when per-DataKind docs (`21`–`24`) get their rewrite (each will be thinner now that it can reference `32c §N` instead of redeclaring Dimension / Measure / Metric shapes). Second rule: when the ratified decisions include both *authoritative* shapes (e.g. `Relationship` struct fields, `AggregationType` roster) and *cross-cutting* rules (e.g. "grain-forbidden-on-complex", "filter-kinds-disjoint"), number the rules in their own independent series (`SR-E-*` separate from the root doc's `SR-*`) so later additions in either series don't perturb the other's numbering.
- **L12 (2026-04-27, ninth pass)** — **Status-bearing filenames and status-bearing directories conflict — pick the directory.** The old layout carried open/closed status in the filename (`<doc>_open_questions.md`) which was correct on day one (one flat directory; the suffix told you the file's purpose) but broke down once individual Q-IDs started closing inside files: a file named `23_open_questions.md` could carry two CLOSED items and twelve open ones, and the filename gave the wrong impression. Three things observed once the directory had ~30 mixed files: (1) finding "what's still open" required opening files one by one; the filename gave no signal beyond "this file has questions." (2) the "all-resolved" file `31b_io_open_questions.md` looked identical in `ls` to the still-active ones — its closure was only visible inside the file's opening line. (3) every cross-doc reference repeated the redundant suffix (`open_questions/15_open_questions.md` says "open" twice). The fix was structural: the directory carries status (`questions/open/` vs `questions/closed/`), the filename carries identity (`15_questions.md`), and `ls` now answers "what's open" / "what's archived" in one glance. Two rules survive the fix: (a) **never encode the same fact in two places** — if status is in the directory, drop it from the filename; if a single piece of metadata varies between files, decide once where it lives (filename vs subfolder vs front-matter) and remove it from the others. (b) **plan for files moving categories** — when a file's status can flip (an `open/` file becomes `closed/` once every Q-ID resolves), the structure must support that movement cheaply. The current structure does: `git mv questions/open/X_questions.md questions/closed/X_questions.md` is one command, history is preserved, every reference inside the file (which uses relative paths to siblings) keeps resolving. Compare to the alternative of splitting closed Q-IDs out into a parallel sibling file: that would have created two files per source doc, and *every* cross-reference would need a "is this in the open or closed file?" disambiguation. The simpler structure is also the more durable one. Third observation (mechanical, but worth recording): a perl `find -exec` pass with ordered substitutions (specific → general, path-prefixed before bare-filename) handled ~250 references in one shot with five hand-fixes for tokens the regex couldn't disambiguate. When a rename is mechanical, treat it as mechanical — write the substitution rules once, run them, then verify with a single `rg` of the old pattern returning zero matches. Don't try to enumerate every reference site by hand; you'll miss some.
- **L11 (2026-04-17, eighth pass)** — A **consolidation doc at the wrong layer accretes drift**. `32c_entities.md` was the right *pattern* (L10) but the wrong *placement*: siting cross-cutting entity struct defs in the `3x` api layer inverts the dependency direction — every `1x` foundations doc that predates it has to reconcile against an `api`-level sibling, and the next author reaching for a struct shape has two canonical homes to choose between. Two concrete consequences observed once the structure grew: (1) two silent duplicate blocks appeared (`18 §3.5` re-declared `Grain` with an extra `Second` variant not in `13 §3.1`; `16 §5.2` re-declared `RelationshipPath` identical to `14b §4.5`), each discovered only during a dedicated audit; (2) `32`'s `refined-by:` grew to include upstream docs (`18`, `15`, `21`, …) because authors reading the file saw `32c` below them and generalized the direction. Three survivable rules: (a) **directionality is structural** — canonical definitions belong in the lowest-numbered doc that owns them, per `00 §8`; a consolidation doc is a presentation concern that sits in the same layer as its owned concepts. (b) **a concept has exactly one `authoritative-for:` home** — `authoritative-for` is a *claim* not an *aspiration*; if two files list the same concept, one of them is wrong and precedence (`00 §4.4`) decides which. (c) **every duplicate code block is a latent drift vector** — the two fixes this pass (`Grain` roster, `RelationshipPath` shape) were zero-risk only because the duplicates happened to match (or nearly match) the canonical home; the next accidental addition could diverge and stay divergent for months. Remedy going forward: whenever a doc needs to show an already-canonical shape for reader convenience (the `3x` api docs exposing foundations types are the dominant case), follow the `INDEX.md` Crate-surface mirroring convention — in-comment pointer to the canonical home, shape must match byte-for-byte, mirror appears once per crate at the `§N Type-level surface` heading. Any violation of those three constraints is a design bug fixable at the canonical home, not the mirror.
- **L13 (2026-04-27, tenth pass)** — **When several fields on a struct co-vary, the right abstraction is a labeled invariant — not a wider-validation rule.** The constraints session had been deferred for two passes because every attempted DSL ended up with 4-5 sub-blocks (`aggregations:`, `dimensions:`, `filter:`, `cardinality:`, `keys:`) each duplicating relationships that were already implicit between the carrier's `agg`, `additivity`, and `expr` fields. The breakthrough was *naming the bundle*: `category: <variant>` lifts the implicit correlation into a labeled enum where each variant ratifies its own implicit-constraint contract (`Additive` ⇒ `agg ∈ {Sum, Count}` ∧ `additivity = Full`; `Snapshot` ⇒ `additivity = Semi(...)` synthesized from body; `Ratio` ⇒ `expr` shape is `numerator / denominator`). Two consequences fall out: (1) the **explicit constraint surface shrinks** — most of what `11 §8` was reaching for is now subsumed by the category's implicit contract, leaving `constraints:` as a narrow refinement layer that can only *narrow* category-implied rules (SR-E-15). The author is no longer redeclaring the relationship between `agg`, `additivity`, and `expr`; the category fixes them. (2) the **planner / adapter contract becomes labeled** — instead of "if `agg = Avg` then planner materializes SUM/COUNT", the contract reads "`MeasureCategory::Average` requires SUM/COUNT materialization in the planner". The latter is greppable, branchable, and survives field renames. The pattern generalizes: whenever a spec edit is reaching for a wider validation rule that would correlate three or more pre-existing fields, ask first whether the correlation is *actually* a category — a finite, named set of co-occurring shapes — and whether lifting it into an enum (with `#[non_exhaustive]` Rust-level forward compat, `#[serde(default)]` for post-v1 fields, and a closed-set author surface) replaces the validation logic with a type-system invariant. dbt MetricFlow / Cube / LookML all converge on the same pattern; semstrait's tenth-pass adoption brings it home for our axis. Two discipline rules survive: (a) **a category enum without `#[non_exhaustive]` is a category enum that will accrete drift** — every category enum + body struct must carry the attribute on day one, even when only three variants are ratified; the cost is one line and the alternative is a breaking change later. (b) **strict-then-loosen on the YAML surface** — v1 strict-rejects unknown categories (Layer 2 / `SR-E-19`); a future major can add a lenient downgrade path under `[TD-CAT-LENIENT]` if forward-read compat becomes a concrete need. The reverse direction (start lenient, harden later) is a breaking change to authoring contracts and not safely available.
